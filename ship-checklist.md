- [ ] **Distribution channel**: direct download (Developer ID + notarization) vs. Mac App Store — see reasoning below, but pick one before building the packaging pipeline
  - **Still `[ ]` because it is Rishab's to record, but it is now a formality rather than a judgement — measured against the built artifact 2026-08-20, and the reality is far past the recorded claim.** The line this project has carried is "six nested `.app` bundles with `us.zoom.*` identifiers". Counting the Release build:
    - **Seven** nested `.app` bundles, not six — `ZMScreenshot`, `CptHost`, `SDK_Transcode`, `capHost`, `aomhost`, `airhost`, **plus a second `aomhost.app` nested inside the first**, which is a bundle inside a bundle carrying the same identifier and a validation problem in its own right.
    - **75 distinct nested bundle identifiers, of which 74 are not prefixed `Rishab-Reddy.Anchor`.** App Store validation requires every one of them to be. The breakdown: 36 `us.zoom.*`, 20 SaaSBee, 8 `zoom.us.*`, 7 `com.*` (including `com.airbnb.Lottie`), 1 `se.curl.libcurl`.
    - **The SaaSBee identifiers arrive in three different casings** — `SaaSBee.*`, `SaaSbee.*`, `saasbee.*` — which is worth knowing only because it is exactly the detail that would defeat a rewrite script keyed on one spelling, if anyone ever thought the rewrite was the way out. It is not; these are vendored binaries Anchor does not build.
  - So the choice is not between two channels with different costs. **There is one channel.** Re-run the count against any future build with:
    ```sh
    find "$APP" -name Info.plist -exec plutil -extract CFBundleIdentifier raw {} \; 2>/dev/null | sort -u
    ```
  - What this does *not* settle, and is the reason the box stays open: the decision has consequences beyond packaging — no StoreKit, so the per-teacher pricing tier in §0 needs Stripe and licence enforcement that do not exist. Recording the channel is one line; the tail it pulls is not.
- [ ] **Pricing model**: free, per-teacher subscription, per-school license — affects whether you need StoreKit (App Store) or your own payment integration (direct)
  - **First numbers put on the table, 2026-08-20 (Rishab): $15–20k/year per online school, $15–20/month per individual teacher.** Recorded as a starting position, not a decision. Three things bear on it:
  - **The school number is the right *shape* — few, large contracts — and probably too high for most of `PROSPECTS.md`.** At $15–20k you need only ~15–20 schools for $300k ARR instead of 150, which is a far more tractable sales mountain. But it is also budget-approval money: a head-of-school or board decision with a purchase order and a procurement cycle, not discretionary spend. Several listed prospects cannot pay it at all — the in-person co-ops are small, and **Kepler Education is independent contractors with no central budget**. This wants tiering by student count rather than one number.
  - **The per-teacher tier prices a product that does not currently exist.** An individual teacher on their own Zoom account cannot sign in at all until the app is published to the Marketplace (§3), and even then gets **no participant scopes, a 40-minute cap on Basic, and no bot** — so no live signal, i.e. the LMS half alone. There is also no payment path: direct download means no StoreKit, so it needs Stripe plus licence enforcement, which is unbuilt. **Do not price this tier before the product for it exists.**
  - **The pilot itself should be free.** Charging a design partner for an unproven tool in its first term buys a small amount of money and costs the candour that is the entire point of a pilot.

## 1. Legal & compliance — do this early, it gates everything else

- [x] **The guard protecting student names in logs had an escape hatch; it is closed and now watched — 2026-08-21.** `RELEASE.md` calls `ReleaseHygieneTests` *"the only thing standing between a student's name and a log file"*, so it was worth asking whether it can be caught being wrong.
  - **It looked like it had a hole and does not, for a reason nobody had written down.** Its list is `print(`, `NSLog(`, `debugPrint(` — while **seven files hold a `Logger`, six of them not exempt, including `ZoomMeetingSDKBridge`, the file the suite was written for**, and `Logger` writes to the same unified log. **The asymmetry is the justification: OSLog renders dynamic strings and objects as `<private>` by default; `print` writes whatever it is handed, verbatim.** A student's name is a `String`, so `Logger` hides it and `print` does not. Numbers stay public, which is right for counts and result codes. That is now in the file rather than in nobody's head.
  - **The real gap is `privacy: .public`, which forces a value past the default.** Audited all **thirty** occurrences: twenty-eight are result codes, counts, HTTP paths, error descriptions and Anchor's own sidecar filenames. `testNoStudentIdentityIsPublishedToTheLog` now fails a `.public` interpolation whose expression names someone in the class, and **deliberately does not ask anyone to justify `http.statusCode`** — a guard that did would teach the reader the list is noise, which is how the real one gets waved through.
  - **Three canaries, each watched failing:** a student's name published, a participant `userName` published in the bridge, and `students.map(\.name).joined()` — aggregate-shaped but not an aggregate, which proves the `.count` exemption is not a loophole. Tests **311 → 312**.
- [ ] **Decide whether a Google Classroom *course name* belongs in a Release log.** The two `.public` interpolations that are neither a code nor a count are `course.name`, logged twice by `ClassroomViewModel` — on sync and on sync failure. It lands verbatim in the unified log, readable with Console.app by anyone with the Mac, which is the threat model `ReleaseHygieneTests` states for itself. **Left alone rather than fixed, because a course name is school data rather than a child's**, the log is local, and "is *this* name too much" is a judgement rather than a defect. The fix is one word — drop `privacy: .public` and let OSLog redact it — and it costs a slightly less useful diagnostic.
